# 文档目录与维护规则

> 文档 ID：`DOC-DOCUMENTATION-RULES-001`
> 生命周期：`GUIDE`
> 制定日期：2026-10-25
> 适用范围：整个产品的人类文档，第一阶段统一维护在本仓库 `docs/`。
> 依据：产品负责人在本次讨论中采纳的最简文档组织方案与模块分工方式；现有机器约束见[文档校验规则](governance/docs-verification.md)。

本文件统一规定文档放在哪里、何时拆分、如何引用与归档。各模块负责人依据本规则迁移和维护内容；总设计与跨模块规则由工作群讨论决定，再由指定维护人回写。

本规则是目录与放置约定的唯一正文来源。[文档门户](README.md)负责导航、责任表和本规则的入口链接。本文规定的是目标结构，不表示目录、模板、责任表或业务规格已经全部建立，也不表示现有文档已经迁移。

## 1. 目标目录

```text
docs/
├─ README.md                 总入口、模块责任表、本规则链接
├─ documentation-rules.md    本文档
├─ product.md                产品总设计
├─ modules/
│  └─ <模块名>/
│     ├─ product.md          模块产品说明
│     ├─ technical.md        模块技术方案
│     └─ <专题>.md           确有需要时增加
├─ shared/
│  ├─ <公共规范或指南>.md
│  └─ templates/
│     ├─ product.md          产品说明模板
│     └─ technical.md        技术方案模板
├─ status/
│  ├─ current.md             当前实现情况、下一步、阻塞
│  └─ release-plan.md        发布顺序、阶段目标、退出条件
└─ archive/
   └─ <原相对路径>           被替代文档、历史研究与实施记录
```

新目录和文件随实际内容按需建立。现有 ADR、治理登记、证据、发布制品、changelog、生成页面与其他机器绑定材料属于保留区，处理方式见第 6 节；上图只列日常维护结构。

在新文档完成承接、相关引用与机器规则完成更新之前，继续使用[产品范围](product-scope.md)、[当前架构](architecture/current.md)、[ADR 注册表](adr/registry.md)、[当前状态](status/current.md)和[现行发布路线](roadmap/release-plan.md)。新的目录分类不改变产品对象归属、实现责任或现有工程门。

## 2. 内容放置边界

| 内容 | 放置位置 |
| --- | --- |
| 产品目标、模块职责、共同对象归属、跨模块业务流程 | `docs/product.md` |
| 单模块目标、用户流程、业务规则、上下游关系、验收标准 | `docs/modules/<模块名>/product.md` |
| 单模块实现方式、数据、接口、技术决定、异常恢复与验证 | `docs/modules/<模块名>/technical.md` |
| 多模块共同遵守的体验、权限、安全、技术和开发运行规则 | `docs/shared/` |
| 当前实现程度、负责人、下一步、阻塞及证据链接 | `docs/status/current.md` |
| 未来阶段范围、优先顺序与退出条件 | `docs/status/release-plan.md` |
| 通用产品说明与技术方案模板 | `docs/shared/templates/` |
| 被替代方案、结束的计划、历史研究和实施记录 | `docs/archive/` |

共同规则由总设计或公共文档定义，模块文档链接对应章节，并写清本模块的适用方式与业务差异。当前实现情况集中维护在项目进度中；模块文档注明关键实现差距并链接进度。

## 3. 模块目录命名

以九个业务模块为分类起点，后续按经讨论确认的实际职责边界调整。

| 模块 | 目录名 |
| --- | --- |
| 账户与工作空间 | `account-workspace/` |
| 卖家知识中心 | `seller-knowledge/` |
| 买家知识网络 | `buyer-knowledge/` |
| 买家发现与资格判断 | `discovery-qualification/` |
| 独立站建设 | `site-builder/` |
| 内容传播与 GEO | `content-geo/` |
| 买家触达与会话中心 | `outreach-conversations/` |
| 机会与 QGO 中心 | `opportunities/` |
| 结果学习与增长优化 | `learning/` |

目录采用稳定的业务名称。负责人、前后端岗位或临时任务的变化只更新责任信息，不因此更改目录。产品模块与代码模块、页面导航分别描述各自视角，不要求一一对应。

## 4. 文件命名与拆分

- 每模块默认以 `product.md` 和 `technical.md` 为主入口，不强制增加模块 README。
- 详细接口、线框、运行手册等确需独立维护时，作为所属模块的专项文件，由主文档链接。
- 按已有内容建立目录和文件，不预建功能目录树、空目录或空模板文件。
- 未决问题先写入所属文档的“待决问题”。普通讨论过程保留来源链接，不为每次讨论生成常驻会议稿或计划。
- 路径使用英文小写 kebab-case，正文标题可以使用中文。
- 当前文档名不带日期、版本号、`final` 或 `latest`；历史记录、发布制品和机器规定的命名除外。
- 文档生命周期与标识沿用[现有校验约定](governance/docs-verification.md)，不另建一套状态词表或平行登记表。

## 5. 引用、维护与归档

模块负责人维护本模块正文。模块内调整自行决定；涉及共同对象归属、模块边界、跨模块流程或全局规则的变更，在工作群同步、讨论决定。变更发起人推动共同结论落档，受影响模块负责人分别更新本模块文档。

确认采用的设计结论直接更新正式正文，并简记决定、理由、影响和讨论来源。尚未决定的内容保留为待决问题，明确现行规则及受影响范围；设计目标与已实现事实分别表述。

归档按以下顺序处理：

1. 判断旧文档中哪些结论仍有效，并明确承接文档。
2. 将有效结论写入正式正文；研究、旧方案与实施记录保留来源关系。
3. 在旧入口或归档索引注明替代关系，更新相关引用。
4. 将历史资料移入 `docs/archive/`，保留其原来相对于 `docs/` 的路径。例如 `docs/research/example.md` 对应 `docs/archive/research/example.md`；不另加按月份重复分类的层级。目标路径已存在时先核对来源，另取可追溯名称，不覆盖已有文件。

尚在使用的专项研究可以留在所属模块，明确其参考性质。文档是否适合归档须结合正文、生命周期和实际引用判断，不能只凭所在目录、文件名或日期决定。

## 6. 保留区与仓库入口

现有 ADR、能力与对象等治理登记、原始证据、发布制品、changelog 及生成页面保留各自的独立职责，由日常入口关联。

涉及测试读取、生成器输出、治理登记来源、CI 路径范围或冻结证据绑定的文件，先核对引用与机器约束，再协调物理迁移。内容负责人负责正文，技术维护人配合处理关联路径与验证；冻结证据保持原有证明内容。

代码旁的 README、接口接入说明、运行手册，以及仓库根目录的 `AGENTS.md`、`CLAUDE.md`、贡献指南和工具配置等保留原位，通过文档入口或所属主题文档链接。

## 7. 模块迁移完成标准

模块迁移完成时，应同时满足：

1. 产品说明和技术方案有明确入口，专项资料可从主文档到达。
2. 与总设计及公共规则一致，未决冲突有记录。
3. 原资料的保留、承接或归档去向清楚，链接有效。
4. 负责人明确，受影响的文档与治理检查通过。

本规则本身不授权批量迁移、删除历史材料、变更机器合同或调整产品范围。具体迁移仍按各自任务范围与仓库既有执行规则推进。
