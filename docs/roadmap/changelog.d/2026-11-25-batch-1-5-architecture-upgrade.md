- 起因：基于 Batch 1.4 现网实跑（run `607b314d`）深度复盘与架构演进方案（`batch14-live-postmortem-and-architecture-evolution-2026-11-25.md`）以及 Batch 1.4-D 实跑（run `8b9ff0fa`）暴露的现场缺陷，系统存在 6 项深层结构性短板：旧迁移 `20261109100000_registry_frames` 漏向运行时角色 `runtime_api` / `runtime_worker` 授予 `registry_*` 表 SELECT 权限导致 `registry_frame` 计划查询触发 `permission denied` 并拖垮整轮发现；41.8% 公司 `country = NULL` 导致 58.2% 联系人缺少国别并在 GDPR Art.14 排期上 Fail-Open（如德国 `Centroplan GmbH` 28 名员工漏排）；L1 快扫用旧版工业泵四门硬套买方摘要并拿卖方产品型号参数误杀 72% 真实光伏 EPC/分销商；卖家官网理解把 `"下载中心"`、`"产品询问"` 等导航菜单误写入 `offering`；JS 菜单站点在首页未露人物链接时缺 `/sitemap.xml` 真实路径发现；专利源用进程级全局 `PATENT_SOURCE_MODE` 一刀切且未分离无隐私企业专利信号，以及 L0 可选搜索引擎缺失败冷却熔断。
- 改动：新增迁移 `20261125090000_registry_frame_runtime_role_select_grants` 为 `runtime_api` / `runtime_worker` 补齐 5 张 `registry_*` 平台表的只读 SELECT 权限并在 `registry-frame.provider.ts` 增加异常 fail-safe 兜底；新增统一国别中枢 `jurisdiction-resolver.ts`（复用五级确定性国别解析与保守 EU/UK Fail-Closed 兜底），在 `company-enrichment-commit.ts` 自动回填 `canonical_company.country` 并写 `field_evidence`，并接入 `public_web`、`model_web_search`、`contact-persist`、`step0-pattern-inference` 与 `battle-csv-builder`；在 `article14-lia.service.ts` 与 `outreach-draft.ts` 增加默认 B2B LIA 一键激活模板与极简多语种 Art.14 首联页脚；重构 `quick-scan.ts` 的 `buildQuickJudgePrompt` 为「买家行业/角色必过 × 卖方参数加分」两层口径并传入推断国别与证据摘要；新增 `offering-noise-filter.ts` 在官网理解落库、首联草稿生成与作战表读出时过滤导航菜单噪音；在 `decision-maker-paths.ts` 增加 `/sitemap.xml` 线性扫描补齐真实人物页路径；在 `bigquery-patents.provider.ts` 支持 `workspace_lia` 按工作区 LIA 门控并导出零 PII 的企业专利信号摘要；新增 `search-engine-health.ts` 给 L0 可选搜索源加 3 次连续失败 120 秒冷却熔断。
- 测试：全量通过新增与受影响 vitest 单测（`jurisdiction-resolver`、`offering-noise-filter`、`search-engine-health`、`company-enrichment-commit`、`quick-scan`、`decision-maker.provider`、`bigquery-patents.provider`、`contact-persist`、`step0-pattern-inference`、`battle-csv-builder`、`public-web-raw-governance`、`public-web-search-first`），API 构建、`lint`、`check-file-budgets`、`governance-module-boundaries`、`governance-unsafe-raw-sql`、`governance-verify`、`copy-fixed-source-impact`、`governance-document-drift`、`docs:verify` 与 `gitleaks` 全绿。
- 未做：Prospeo / Step 0 正式纳入 `ControlledEnrichmentProvider` 支付安全通道与 `directory` 三层分级准入留下一批次独立推进，本 PR 不修改任何 sha256 锁定核心文件与数据库表结构。
