# 寻源提速：快扫 / 深挖两档设计

> 生命周期：`DRAFT`
> 依据：产品负责人 2026-11-04 拍板「先设计快扫/深挖两档」；现状实测：上一轮成功 run 70 分钟（16 组查询、84 家公司、88 次逐家 fit 判定，仅 3 路并发、单次 26–55 秒），当晚两条 run 因上游 429 与 5/25 分钟退避等待拖到 2 小时以上。

## 一、目标（按用户感知定义）

- **快扫**：点「开始找买家」后 **≤8 分钟**，界面上出现第一批「可判断」的候选公司（目标 ≥5 家，来自结构化意图源与搜索的粗筛），用户可以先看名单、先标记。
- **深挖**：对快扫选出的子集（粗判 match/weak）继续做官网画像、精判、信号与联系人，**≤15 分钟**完成；期间结果增量更新，不阻塞快扫名单。
- **不降低质量门槛**：制裁/抑制门、来源治理、lawful-basis 门不变；深挖后的精判与现状一致。

## 二、现状与时间构成（实测）

| 阶段 | 现状 | 时间构成 |
| --- | --- | --- |
| 搜索企业 | 16 组查询、每批 2 组 | 每组=元搜索+抓页+LLM 抽取（5 并发），受模型延迟支配 |
| 官网画像 | 每家公司 2 页+渲染+模型，30 天 TTL | 慢站吃满 15 分钟时间盒 |
| fit 判定 | 逐家，`FIT_CONCURRENCY=3`，单次 26–55s（最慢 134s） | 88 家 ≈ 20 分钟，最大单项 |
| 信号/监听/联系人 | 串行接在 fit 后 | 依赖 fit 结果集合大小 |
| 429 退避 | 5 分钟 / 25 分钟 | 上游抖动时直接决定总时长 |

结论：慢在「逐家模型调用 × 低并发 × 串行阶段 × 退避等待」，不是单点故障。

## 三、方案：同一 run 内两档（quick → deep）

一次点击、一条 run 记录、一个预算 Grant；快扫产出的线索先可用，深挖在同 run 内继续并原地升级。

### 3.1 快扫（新增）

1. **结构化意图源优先**（新增 provider 候选，见 §五）：
   - 海关提单（ImportYeti 类：美国海运进口记录，公司级、免费公开来源）→ 「近 12 个月有进口记录的公司」天然是高置信候选，**无需逐家 LLM** 即可进入名单；
   - 展会参展商名单（已有 trade_fair/mapyourshow，可直接复用）；
   - 现有 SearXNG+抽取通道保留，作为兜底。
2. **规则预筛**（不调模型）：域名词表、行业/产品关键词命中、注册地/目标市场命中 → 去掉明显不相关。
3. **粗判**：对通过预筛的公司跑一次「快判」——输入只用已有结构化事实（来源、域名、行业、查询命中词），输出 match/weak/mismatch 与一句理由。**先逐家 flash 直判（不改合同），第二阶段再批量化（一次 8–10 家）。**
4. **快扫完成点**：把 match/weak 物化为 Lead（`fitReasons.tier='quick'`，queue=needs_review），run stats 写 `phases.quickDoneAt`。界面阶段卡翻到「快扫完成·可先看名单」，买家线索页标「待深挖」。

### 3.2 深挖（现有能力的收窄复用）

5. 输入集合 = 快扫的 match/weak（mismatch 不深挖；用户可在界面上手动「捞回」个别 mismatch）。
6. 依次跑：官网画像（缓存优先）→ 精判（沿用现 fit，`fitReasons.tier='deep'` 覆盖粗判）→ enrich/GLEIF → 信号/监听 → 联系人（lawful-basis 门照旧）。
7. 每阶段完成增量更新同一批 Lead（`fitVerdict`/`scores`/状态原地升级），run stats 写 `phases.deepDoneAt`。**深挖中途用户即可见每家的升级状态。**

### 3.3 编排与兼容

- workflow 用 patch 守卫新增两档编排（旧历史 replay 不变）；快扫开关用 env（`DISCOVERY_QUICK_SCAN=on/off`）默认开。
- 预算/租约：仍为一个 run 一个 Grant；快扫早了结但深挖继续消耗，同一上限。
- 失败语义：快扫失败→如实 FAILED（收据逻辑沿用 #759 修复）；深挖失败→已产出的快扫名单保留可用（run 记 PARTIAL，failure.stage=deep）。

## 四、触点（代码与数据）

- `apps/api/src/temporal/discovery.workflow.ts`：新增 quick/deep 阶段编排与 patch。
- `apps/api/src/temporal/discovery.activities.ts`：新增 `qualifyFitQuick`（或 qualifyFitForRun 的 quick 模式）与结构化源落地；stats 增 `phases`。
- 新 provider：见 §五（先做 1 个，按接入评估结果定）。
- `apps/web`：寻源页阶段卡（快扫/深挖两行时间戳与进度）、买家线索页「待深挖」标签与「捞回」动作；i18n。
- 契约：`fit-judgment/v1` 先复用（粗判=同一合同、输入更少）；批量判定属第二阶段，单独改合同。
- 无数据库迁移（用 `fitReasons.tier` + stats 扩展；如后续需要按档过滤再加列）。

## 六、风险与取舍

- 粗判误杀：只把明确 mismatch 排除（规则+模型双闸），weak 一律进深挖；界面提供「捞回」。
- 快扫名单质量：结构化源（提单/展会）与搜索来源分开展示来源标签，用户能判断可信度。
- 两档语义带来的统计复杂：stats `phases` 与 Lead `tier` 足够表达，不引入新表。
- ImportYeti 接入若条款不允许自动化访问 → 退回「用户手工上传/粘贴企业清单」的导入通道（P2 备选），不绕条款。

## 七、验收标准

1. 真实 run：快扫名单在 ≤8 分钟内出现（≥5 家公司，含来源标签），买家线索页可见「待深挖」。
2. 深挖在 ≤15 分钟内把快扫名单升级为精判结果；期间界面增量可见。
3. 同 run 预算不超上限；失败语义符合 §3.3。
4. 旧历史 replay 测试与既有全量单测全绿。

## 八、TDD 步骤（实施时）
