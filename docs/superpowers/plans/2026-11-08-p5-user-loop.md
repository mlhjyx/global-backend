## 1. 背景与目标

获客闭环 P1–P4 已上线，P5 收尾三个断点，代码事实如下：

### 1.2 目标（对应 P5 验收）

1. **alerts 站内先行（Q21：不发邮件）**：在既有铃铛体系上补齐「配额告警」与「制裁 hold」两类系统通知；一条真实事件能落库并在租户端可见可点。
2. **引导 Claim 草稿**：为新用户/新空间从卖家档案（注册引导填写的主营产品/行业/目标市场）确定性生成可审批的 Claim 草稿（NEEDS_REVIEW），走既有审批模型；批准 ≥1 条后 ICP 生成不再被 `NO_APPROVED_CLAIMS` 卡；老空间可显式补齐。

## 3. 方案 A · alerts 站内通知

### 3.1 SoR 与事件

- **SoR**：gain-saas `notification` 表（引擎不存通知）；引擎只负责事实事件。
- **不新增事件类型**：全部消费既有对外事件 + SaaS 事实表。

| 触发 | 来源（既有） | notification.type | 标题（zh；en 随 P6） | 深链 |
| --- | --- | --- | --- | --- |
| run 终态 DONE/PARTIAL/FAILED/CANCELLED | `DiscoveryRunCompleted`（已消费） | `DiscoveryRun*`（现状） | 现状文案 | `/runs/:id` |
| 新线索 | `LeadQualified`（已消费） | `LeadQualified`（现状） | 现状文案 | `/leads?queue=recommended` |
| **制裁 hold** | `LeadsScored.payload.queues.sanctions_hold > 0` | `SanctionsHoldDetected`（新） | 「有 {n} 家线索命中制裁名单，已隔离，需管理员复核」 | `/leads?queue=sanctions_hold`（该队列仅管理员可见，`leads/index.vue:49`） |
| **配额预警** | 消费 tick 末尾现算：花费或 run 次数的窗口使用率 ≥80% | `WorkspaceQuotaWarning`（新） | 「额度提醒：已使用 {dim} 的 {pct}%（{used}/{cap}），接近上限」 | `/settings`（暂无专区，开放问题 D-c） |
| **配额耗尽** | 同上，使用率 ≥100% | `WorkspaceQuotaExceeded`（新） | 「本期额度已用完，新的寻源任务将被暂停」 | 同上 |

### 3.2 规则细节

- **制裁 hold**：`derive()` 增加 `LeadsScored` 分支，读 `payload.queues.sanctions_hold`（number），>0 才写一条通知，`refId = aggregate_id（ICP id）`；同一事件重复投递由 `event_inbox` 吸收，天然不重复。真命中复核（`POST /leads/:leadId/sanctions-review`）是管理员本人操作，不另发通知。
- **配额**：`consumeWorkspace` 每轮结束时调用 `evaluateQuotaAlerts(tx, workspaceId)`：
  - 读 `workspace_budget_policy`（无行/`enabled=false` 直接跳过——存量空间默认豁免，迁移口径 `20261104050000_workspace_budget_policy/migration.sql:22`）；
  - `WORKSPACE_QUOTA_ENFORCE=false` 时跳过（未强制的配额不吓唬用户）；
  - 窗口同策略：`since = now - windowDays`；花费取 `cost_ledger.amount_micros` 求和，次数取 `discovery_run_link` 计数（与 `WorkspaceBudgetPolicyService.evaluate` 同口径）；
  - 取两个维度使用率的最大值：≥100% → `WorkspaceQuotaExceeded`；≥80% → `WorkspaceQuotaWarning`；
  - **去重**：同 workspace + 同 type 在窗口内已有通知则跳过（每窗口每档一条；下一窗口可再提醒）。
- **反淹没**：不为每条 `ClaimApproved/Revoked/Expired` 发通知；不做理解完成通知（见非目标）。
- **读侧不变**：`notifications.controller.ts` 的 workspace 过滤与已读逻辑不动，仅扩展 `linkFor()` 映射新类型。

### 3.3 闭环位置（计划 §17.6/§17.9）

- 能力地图「租户/身份/额度」与「资格/评分/制裁」两行的「闭环位置」= 全环边界与预算、Qualify：本方案补的是这两段的**消费端**（§17.9 明列的缺口③「通知中心（alerts）的消费端补口」）。
- 不产生新业务对象，不改任何状态机。

### 3.4 负向测试

- 跨租户不可见：A 空间的通知不出现在 B 空间列表（现有 controller 已按 workspaceId 过滤，补一条测试锁住）；
- 重复投递：同 `event_id` 重放不产生第二条通知（event_inbox 幂等）；
- 豁免空间：`policy.enabled=false` 或 enforce=false 时不产生配额通知；
- 无 hold：`queues.sanctions_hold=0` 时不产生制裁通知。

## 4. 方案 B · 引导 Claim 草稿

### 4.1 触发点

1. **建档时自动（主路径）**：引擎 `POST /companies` 同事务内，从注册引导字段派生草稿（company.service.create 调用纯函数）。覆盖「新用户/新空间」。
2. **显式补齐（存量空间）**：新引擎端点 `POST /companies/:companyId/claim-drafts`（幂等，无 Grant，见 §6），公司档案「企业事实」面板加「从档案生成事实草稿」按钮；SaaS 侧用**独立租户控制器**代理（不新增 BFF routes 表条目——避免触碰主会话 M2.0 正在改的 `bff.module.ts`/`app.module.ts`/`routes.ts`）。

### 4.2 确定性映射（无 LLM、零预算、零外呼）

| 档案输入 | Claim.type | statement | 说明 |
| --- | --- | --- | --- |
| `offering.name`（每个产品一条） | `capability` | `主营产品/服务：{name}` | 含 onboarding 与理解抽取的 Offering；同名去重 |
| `company.industry` | `company_fact` | `所属行业：{industry}` | |
| `company.targetMarkets`（非空） | `market` | `目标出口市场：{DE、FR…}` | 一条汇总 |

不派生：`businessEmail`（联系方式、含个人数据可能，且非 ICP 事实）、`summary`（来源是抽取，理解路径已自带 Claim）、`publicContacts`（PII）。

- 证据：一条 `KnowledgeSource(type='onboarding', uri='onboarding:{companyId}', status='PARSED')` + 每条 Claim 一条 `Evidence(snippet='注册引导填写', confidence=1, fetchedAt=now)`，形态对齐 `ClaimService.createManual`（`claim.service.ts:173-208`）。
- **不带 `originKey/factKey`**（A4）：保证可直接审批，不触发 `CLAIM_BRIDGE_REQUIRED`。
- 状态 `NEEDS_REVIEW`，confidence=1（用户自填事实）。

### 4.3 幂等与并发

- 去重键 = 归一化 statement（trim + 空白折叠 + 小写），对公司下**非 REVOKED** 的既有 Claim 去重；REVOKED 不复活（用户明确拒绝过）。
- 端点内先 `SELECT … FOR UPDATE` 锁 `company_profile` 行再读后写，双击/并发安全。
- 建档路径天然只执行一次（同事务）。

### 4.4 打通 ICP 与公司激活

- 批准 ≥1 条草稿即满足 `NO_APPROVED_CLAIMS`；ICP 提示词继续消费 `claims`（`[type] statement`），草稿类型在既有词表内（`ai-tasks/task-registry.ts:159`）。
- 批准 ≥3 条触发公司 `REVIEW → ACTIVE`（既有阈值 `ACTIVATION_MIN_APPROVED_CLAIMS=3`，`claim.service.ts:405`），与「知识充分性」方向一致。
- 前端零改动即可审批（公司档案事实面板已具备），本轮只加「生成草稿」按钮与空态引导。

### 4.5 闭环位置与演示脚本

- 闭环位置：Understand / Target 输入（§17.6 卖家资料库与公司理解两行）；属 E2E-1 主链路的前置修复。
- 演示：新空间完成向导（2 产品+行业+2 市场）→ 档案出现 5 条待审事实 → 批准 3 条 → 公司 ACTIVE → 生成 ICP 成功 → 发起 run。
- 负向：跨租户 404；空档案（无产品/行业/市场）不产生任何行；重复调用 `created=0`；REVOKED 不复活。

## 5. 方案 C · 错误文案表

### 5.1 唯一真值与接线

- 词表唯一真值仍是 `packages/shared/src/errors.ts`（不复制进引擎；引擎错误码即契约）。
- 接线三处：
  1. **补码**：新增 18 个租户面高频码（§5.4 表）；
  2. **SaaS 自抛错统一挂 userCopy**：`GlobalHttpExceptionFilter` 对 `HttpException` 响应做规范化——`{error:{code}}` 且无 `userCopy` 时附 `copyForError(code)`（一处覆盖 guard/控制器/引导等全部自抛错，含 `bff.module.ts` 抛出但本会话不改该文件的 `ONBOARDING_INCOMPLETE`）；
  3. **前端三层呈现**：`failureText()` 增加 `why`；新增共享组件 `apps/web/src/components/error-notice.vue`（title/why/next + `<details>` 技术详情：错误码），接入两处高频面（找买家·生成 ICP 弹窗、公司档案·事实面板）；全局 toast 维持 title+next 不改交互。
- 英文文案：现状 userCopy 为中文直出（前端虽发 `Accept-Language`，词表无英文）。本轮保持一致（中文先行），英文表随 P6 统一（开放问题 D-f）。

### 5.2 为什么不把词表放引擎

引擎的错误码是机器契约（`operation-descriptions.ts` 已逐条登记）；文案是 SaaS 呈现层职责，放 `packages/shared` 可被 BFF 与未来前端共用，避免两处漂移。

### 5.3 覆盖判据（单测锁定）

- `ENGINE_ERROR_COPY` 每条 title/why/next 均非空；
- 租户面高频码清单（常量数组）必须全部在表内（新增码忘了配文案即红）；
- 未登记码 fallback 行为不变；
- 过滤器：自抛 `VALIDATION_ERROR`/`NO_APPROVED_CLAIMS`/`WORKSPACE_DISABLED` 带 userCopy，且不透传堆栈。

## 6. 接口/事件契约

### 6.1 引擎新端点（code-first OpenAPI）

`POST /api/v1/companies/:companyId/claim-drafts`
- scope：`acquisition:review`（与手工录入事实一致；SaaS saas-member/saas-admin 均含该 scope，运行时 `AUTH_ROLE_SCOPE_MAP_JSON` 已核对）。
- 不消费 Execution Budget Grant：纯确定性本地写入，无模型/无外呼/零成本（与 `POST /companies/:id/claims` 一致）。
- 响应 `200 {data:{created:number, skipped:number, claims:ClaimDto[]}}`；跨租户/不存在 → 404 `NOT_FOUND`。
- 语义：按 §4.2 映射补齐缺失草稿；重复调用不再新增。

### 6.2 SaaS 新端点（独立租户控制器，不动 BFF 路由表）

`POST /api/companies/:companyId/claim-drafts`（TenantGuard，admin/member）
- 代理到引擎 6.1；错误经 `EngineHttp.toClientError` 转三层文案；
- 注册在 `tenant.module.ts`（新增 `claim-drafts.controller.ts`），**不触碰** `bff.module.ts`/`app.module.ts`/`routes.ts`（主会话 M2.0 在飞，任务卡明令；如主会话要求改走 routes 表，再行裁决）。

### 6.3 通知类型（字符串，无迁移）

`SanctionsHoldDetected`、`WorkspaceQuotaWarning`、`WorkspaceQuotaExceeded`；`linkFor()` 与前端 `basic.vue` 映射同步扩展（中英双语文案进 `locales/*/gainos.json`）。

### 6.4 不改的契约

`LeadsScored`、`DiscoveryRunCompleted`、`ClaimApproved/Revoked/Expired`、`ICPActivated` 等事件形状一律不动；`GET /events` 与 ACK 协议不动。

## 8. 权限与合规

- **RLS/租户隔离**：全部读写走 `withWorkspace`（引擎）与 workspaceId 过滤（SaaS）；无新表；无跨租户路径。
- **PII**：草稿只含企业级业务事实（产品名/行业/目标市场），不含 `businessEmail`；通知标题只含计数与额度数字，不含公司名/人名；技术详情只放错误码，不放请求体。
- **DSR**：草稿挂在 company 下，随既有级联（`claim` onDelete Cascade）；无新增保留面。
- **合规姿态**：制裁通知只是提醒管理员复核，不改变第五门 hard-stop 语义。

## 9. 预算与成本

- 草稿生成：零模型调用、零外部调用、零 Grant 消费。
- 通知：零外部成本（站内）；配额评估为两次聚合查询/workspace/tick（2 分钟一次），可忽略。
- 事件消费频率不变。

## 10. 迁移、回退与部署顺序

- **零数据库迁移**（无新表/列/索引）。
- **零新增 env**；行为开关不单设（SaaS 侧通知派生随发布生效；如出问题可 revert）。
- 回退：revert 引擎 PR（端点与建档派生消失，已生成草稿留在库里、无害）与 SaaS PR（提示与通知停止产生）；已落库通知可由租户自行删除。
- **部署顺序：引擎先、SaaS 后**（SaaS 依赖新端点；SaaS 的通知派生只依赖既有事件，反向部署也不会坏，但按钮会 404）。
- 发车按计划 §0.3：需产品负责人明确指令；纯代码无迁移，可 `--drain` 排空切换。

## 13. 联网研究（§0.6 第 3 项）

- **站内通知产品模式**：B2B SaaS 的共识是「应用内收件箱=事实记录，邮件/推送只是降级通道」，按可行动性分档、突发事件合并成摘要、未读计数必须诚实；逐条通知是最常见的噪音来源。本方案据此只收系统事件、制裁/配额各合并为一条，并沿用既有铃铛（[Humbleteam: B2B SaaS notifications](https://humbleteam.com/blog/b2b-saas-notification-design)、[SaaS UI: notification UX patterns](https://www.saasui.design/blog/saas-notification-toast-ux-patterns)、[Slack Engineering: rebuilt notifications](https://slack.engineering/how-slack-rebuilt-notifications/)）。
- **错误文案三层法**：「发生了什么 / 为什么 / 怎么修」是 Twilio Paste、Semrush Intergalactic、Neo4j Needle 等设计系统的标准解剖；主文案不出现错误码，码放末尾/技术详情。本方案的三层词表 + 折叠技术详情与之对齐（[Twilio Paste error state](https://paste.twilio.design/patterns/error-state)、[Semrush Intergalactic errors](https://developer.semrush.com/intergalactic/content/errors/errors)、[Neo4j Needle error messages](https://neo4j.design/40a8cff71/v/37015/p/308ccd-error-messages)）。
- **结论**：借（三层文案与通知分档模式）、集（沿用现有 Notification/事件脊梁/词表）、建（草稿合成这一处新逻辑）、避（邮件、通知偏好、全站前端重构均不进本轮）。

## 14. 给产品负责人的说明

- **得到什么**：新用户建档后即有可审批的企业事实草稿，不再被 `NO_APPROVED_CLAIMS` 卡在找买家页；配额接近/超限与制裁 hold 会在站内铃铛提醒；租户高频错误从「操作没有成功」变为「发生了什么/为什么/怎么办＋可展开技术详情」。
